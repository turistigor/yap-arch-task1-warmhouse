### 1. Описание функциональности монолитного приложения

Необходимые пояснения терминов:

Датчик - устройство, сочетающее в себе функции измерения физической величины и управления ею через получение целевого значения.

Метаданные датчика - набор редко изменяемых атрибутов датчика (имя, тип, положение, единицы измерения) в базе данных.

Текущее состояние датчика - запись в базе данных об активности (active/inactive), значении измеряемого параметра и время последнего обновления.


#### Управление отоплением:

- Пользователи могут управлять целевой температурой конкретного датчика;
- Пользователи могут получить полный список датчиков, поддерживаемых системой;
- Система поддерживает подключение/отключение/изменение датчиков.


#### Мониторинг температуры:

- Пользователи могут получить значение температуры от конкретного датчика;
- Пользователи могут получить значение температуры в конкретном месте.


### 2. Анализ архитектуры монолитного приложения

**Язык программирования** : Go (Gin HTTP web framework).
**База данных** : Postgresql.
**Архитектура** : монолитная.
**Взаимодействие**: синхронное REST API для пользователей и администраторов системы.

### **4. Проблемы монолитного решения**
- в условиях необходимости поддержки новых типов устройств могут возникнуть трудности:
	- синхронизации разработки, которые приведут к долгим релизным циклам и повысят риск ошибок;
	- усложнения кода, что приведет к увеличению релизных циклов и повысят **риск ошибок;
	- ухудшения надежности: ошибка в одном компоненте приведет к отказу всей системы;
- в условиях переезда с on-premise на SaaS и роста числа пользователей могут возникнуть трудности:
	- обновления из-за того, что в монолите обновляются все компоненты разом;
	- масштабирования из-за потенциально разного роста нагрузки на разные части системы (например, телеметрия и управление устройствами);
- пока не актуальны, но с течением времени могут возникнуть трудности:
	- обновления на новые технологии из-за необходимости согласовать и синхронизировать переход в рамках всего приложения.

# Задание 2. Проектирование микросервисной архитектуры

В тексте и на схемах используются следующие термины и сокращения:
- physical (phys) devices - физические устройства (датчики, приводы, актуаторы, нагреватели);
- commands (cmd) - команды управления устройствами (увеличь температуру, закрой ворота);
- operations (ops) - операции, которые могут быть проведены над сущностью. Обычно CRUD, но не всегда;
- telemetry (tm) - данные от устройств, отправляемые регулярно (температура, потребление энергии, положение ворот);
- external (ext) - внешний по отношению к текущему контекст (Ext API - внешний интерфейс системы для пользователей).

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
